Afkter champion-plan editor redesign

November 8, 2026 · Design approved by the player. Avalonia, the interaction contracts, unified shell and name-first initial scope are accepted. The implementation plan and task decomposition are awaiting review; no production implementation has started.

Intent

The existing plan editor works but requires too many indirect operations and is not practical or polished enough. Build a simple, understandable editor for players who are not technically experienced. Browsing must support recognition and inspiration when a player cannot recall a champion name. Establish a durable interaction model before implementing the production interface; do not repeatedly redesign it through cosmetic patches.

Agreed product decisions

  • Show all five roles together, each with ranked pick and ban lists, beside a persistent champion catalog.
  • Names remain visible. An empty search shows champions immediately; typing narrows the same list. Portraits are optional and the editor must work without them.
  • One optional catalog filter: All, Top, Jungle, Middle, Bottom, Support. Champions may belong to multiple roles. The filter changes browsing, not assigned roles or permitted plan choices.
  • Drag a catalog champion into a plan. Drag within one list to reorder. Drag between lists to copy and preserve the source; removal is explicit.
  • Click a list to select its clearly highlighted destination, then click a catalog champion to append. If already present, highlight the existing entry instead of duplicating it.
  • Click and keyboard alternatives accompany drag/drop. Keep the interface simple, without specialist gestures or extra modes.
  • A champion-page shortcut opens the app directly on that page. No additional dashboard is requested.
  • Use Avalonia, following two independent investigations. The player values its Linux development workflow and also wants to explore the framework. React with modern WebView2 was a credible alternative, not a requirement.
  • The five-role board and right-hand catalog prototype establish a working direction, not frozen colors, spacing or styling.

Approved scope

Implement one Avalonia desktop shell with Champions and Settings destinations, retaining the tray as a quick-control surface. Migrate window activation, tray lifecycle, timers and shutdown ownership from the WinForms context; reuse the existing Core, diagnostics, discovery/transport behavior and persistence. The unified shell proposal is accepted through approval of this design. Avoid embedding two UI frameworks or introducing a separate editor process and settings writer.

The initial production editor is name-first, without repeated decorative initial badges, portrait downloads, skin selection or image settings. The name-first initial scope is accepted through approval of this design. The layout should not depend on image availability. Adding artwork later is a separate product decision, not a requirement to keep the prototype's badge treatment.

Window and tray workflow

  • Preserve startup as tray-resident and disarmed. Opening Champions or Settings from its tray shortcut creates or activates one application window at the requested destination. Repeated shortcuts reuse that window and the same runtime services.
  • Closing the editor window hides it and leaves monitoring/arming unchanged. Preserve search, filter and destination selection during the running session. Explicit Exit cancels and drains monitors, attempts the final plan save, disposes diagnostics/transport and terminates.
  • The application runtime owns one RolePlanService and shared catalog, controller and monitors independently of view lifetime. All Exit/Stop/Dispose paths await one shared shutdown completion, including cancellation/drain, final save attempt and resource release; noticing that another caller began shutdown is not equivalent to completion. Windows and Settings never create independent writers for the plan file.
  • This work does not add a process-wide single-instance or second-launch forwarding feature; the existing app has no such contract. No new external deep-link protocol is required.
  • Settings preserves current live ready-check delay, manual-pick policy, advanced timing, reset, recovery and retry behavior. Present basic controls first and keep advanced timing collapsed. No Apply/Save button is introduced.

Editor layout and state

Use a compact “Champion plans” heading, Champions/Settings navigation and the short explanation “First available champion is tried first.” Avoid the prototype’s oversized slogan. Use five stable role rows, a pick-priority lane and ban-priority lane in each, and a right-side catalog with readable role and column headings. Number plan entries starting at 1; first means highest priority. Keep champion names readable. Normal desktop sizes should show all five role headings at once; clamp the default window to the available work area. Each priority lane stays single-line, shows its entry count, and scrolls horizontally with an obvious overflow cue or scrollbar and automatic reveal of the selected/insertion position. Do not wrap chips or shrink champion names to squeeze more into the board. Smaller work areas may scroll the board while the catalog remains usable. Exact dimensions, colors, typography and control composition belong to the builder and are not dictated by the prototype.

The catalog is alphabetic when search is blank, supports immediate case-insensitive partial-name filtering, and combines search with the selected role filter. Start at All and Top/Picks as the selected destination. Label the catalog filter “Browse by role: All” and put a distinct “Add to: Top · Picks” destination line immediately above the results, paired with the matching lane outline. Keep these meanings distinct in accessible names and do not rely on color alone. Catalog rows prioritize readable names and a restrained plus affordance over decorative badges. Changing the destination does not reset search/filter or silently constrain the catalog. Clearing search restores filtered browsing. Show a short empty-result message when necessary.

Search, role filter, selection, focus and drag preview are presentation state, not saved plan revisions. A selected plan entry is identified by role, pick/ban list and champion together, independently of catalog selection and insertion destination. Changing the destination cannot retarget an existing selection or focused-entry keyboard command; if the original entry disappears, do not silently select another occurrence of the same champion. Keep technical champion IDs and revision numbers out of ordinary editor flows; retain them in diagnostics. Keep one persistent save-status area visible across the editor/app: “Saved”, “Saving…” or “Couldn’t save · Retry”. On failure explain that changes remain active but are not saved. Transient add/reorder/duplicate feedback uses a separate nearby action-feedback area and never replaces the save state. Empty lanes offer “Add champions”; explain once that empty plans supply no action and fully unavailable priorities have no unconfigured fallback. The offline editor must not imply it knows current draft availability.

Interaction contract

  • Catalog drop: copy the champion into the indicated destination position, or append on an empty/end target. Source catalog remains unchanged.
  • Same-list drop: move the existing entry to the indicated position, resolving indices from stable champion identity and the current list at commit. Dropping in its existing position is a no-op.
  • Cross-list drop: copy into the indicated position without removing the source. This also applies between picks and bans. A champion may be present in multiple lists; do not invent global exclusivity rules.
  • Duplicate destination: for click or drop, retain the existing list order, reveal/highlight the existing entry, and provide brief contextual feedback such as “Already in Top picks at #2”. Do not duplicate or remove it.
  • Click alternative: click a lane or its Add control to select the destination; click a catalog entry to append. A successful edit selects/reveals the affected plan entry and destination.
  • Reorder/remove alternatives: selected entries use one stable Earlier/Later/Remove strip, not repeated buttons on every chip. Identify its full subject, for example “Top · Picks · Garen · Priority 1”. Provide keyboard equivalents and meaningful accessible names. Keep destination outline, selected-entry highlight and actual keyboard-focus indication visually distinct. Catalog additions/duplicates reveal and select the affected entry without stealing focus from the browsing/search control; plan reordering retains focus on the moved entry, and removal focuses a neighboring entry or the lane Add control if empty. Delete removes only a selected plan entry, not text while the search field owns focus. Disabled boundary actions are apparent.
  • Drag feedback: use a movement threshold, a narrow insertion marker, target highlighting and accurate copy/move effects with visible “Copy” or “Move” feedback. These states must remain distinct from the destination outline and selected-entry highlight. Support overflow autoscroll. Invalid/outside drops and Escape cancel without plan changes.
  • Commit boundary: publish one complete immutable edit on valid drop/command, never on drag-over or unfinished movement. Copy modifies only the destination, so no two-list remove/add transaction is needed. Cancel a stale source reorder if its champion is no longer in the current source list; revalidate current target membership before committing any drop.

Offline catalog and role data

Continue using Afkter's bundled champion IDs/names. Export the role mapping from the user-owned JoinGameAfk catalog into a small bundled data asset, without importing its refresh/storage services. Source inspection at JoinGameAfk 674d092 found 173 numeric keys covering exactly all 173 IDs in Afkter's Data Dragon 16.22.1 bundle; 281 role memberships. Translate Mid to Middle and Adc to Bottom; use numeric Key, not the string champion alias. Preserve applicable MIT attribution.

These are curated discovery hints, not live popularity or eligibility. Role filtering never prevents adding any champion to any plan. Update the mapping with releases. A new/unmapped champion remains findable under All and search, without guessed role tags. If role metadata fails validation, retain All browsing and existing plans, disable the role filter and explain its unavailability briefly. No live client or network request is needed for normal editing. The bundled identity-catalog failure/recovery contract remains unchanged.

Architecture and compatibility

  • Use .NET 10, a pinned stable Avalonia release, standard controls/templates and a small MVVM presentation layer. The prototype's compact programmatic code is a disposable exploration, not a production architecture to copy wholesale.
  • Keep validation, effective revisions, persistence, timing/policy and automation authoritative in Core. Views/view models own only presentation and translate user commands. One owned refresh loop per window runs while visible, stops on hide/exit, resumes on reopening, and is not duplicated by navigation or repeated activation. Use the same commands for pointer and keyboard paths.
  • Preserve legacy AFKtor technical/storage identities, role-plans.json schema/data and settings.json timing migration. Existing saved priorities, policies and timing must load unchanged.
  • Preserve starts-disarmed, reconnect admission, cancellation, one-attempt ready checks, current live-settings behavior and read-only diagnostic APIs. Existing shipped draft-write verification gates remain unchanged by the UI migration.
  • Retain current discovery cadence and cancellation/drain semantics when replacing WinForms timers. UI close/reopen must not rebuild or dispose application services. Do not move network/persistence waits onto the UI thread.
  • Provide a Linux development/preview composition using the actual production views with isolated sample/local data and no League discovery or automation. It must not write real Windows profile data or claim native client verification.
  • Keep packaging/build instructions reproducible from dotnet CLI. No Visual Studio designer, browser runtime, JavaScript toolchain or paid Avalonia component is required. Installer/update-system changes are outside this work.

Verification proportionate to this project

Keep tests focused on meaningful behavior: destination copies and source preservation, reorder/drop commit boundaries, duplicate/no-op behavior, cancellation, focus/keyboard alternatives, role mapping and existing-data compatibility. Reuse the existing core suite and run the repository's full appropriate checks once for integration. Do not multiply tests for purely cosmetic changes.

On Linux, run the actual Avalonia editor and inspect browsing with blank search, Top/Tryndamere discovery, adding, insertion feedback, same-list reorder, cross-list copies, duplicates, deletion while search is focused, overflow, window resizing and visible save failure/retry. Verify the development host uses isolated data. Check service lifetime and window activation with controlled dependencies where practical.

Occasional Windows use should check tray activation/reopening, window-close versus Exit, keyboard/drag/drop, high DPI and settings recovery. Missing native checks are reported as pending, not prerequisites for every development iteration. This UI project does not complete original draft-companion ticket 07 or enable live draft writes.

Non-goals

No new automation policy, queue mode, profiles, import/export UI, multi-selection editing, drag modifier modes, theme/customization panel, portrait downloader, skin browser, general dashboard, statistics feed, process-wide single-instance system or installer/updater project.

Its five hierarchy/readability recommendations were accepted for incorporation: explicit filter/destination labels, compact name-first presentation, deliberate single-line overflow, distinct destination/selection/insertion/focus states, and contextual outcome feedback separate from persistent saving status.
