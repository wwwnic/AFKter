Afkter champion-plan editor redesign

Design discussion in progress · November 8, 2026. Avalonia is selected and a throwaway interaction prototype is authorized; this is not approval to replace the production UI.

Intent

The current editor works but requires too many indirect operations and is not practical or polished enough. Design a simple, understandable interface for players who are not technically experienced. Consider the interaction carefully before building; avoid repeated redesigns.

Confirmed direction

  • Show all five roles together, with ranked pick and ban lists and a searchable champion catalog.
  • Support dragging champions into lists and reordering, with click and keyboard alternatives.
  • A champion-page shortcut should open the app on the appropriate page. Do not assume the player requested a broader dashboard or navigation redesign.
  • Keep champion names visible. Browsing helps recognition and inspiration when the player cannot recall a name; do not require a successful typed search to discover champions.
  • Champion portraits are optional; the interface must remain useful without them.
  • Include one optional catalog filter: All, Top, Jungle, Middle, Bottom, Support, alongside name search. Champions may appear in multiple roles. The player approved this filter while emphasizing a simple interface.

Existing contracts to preserve

Existing ordered role plans, live application and autosave remain the foundation. A completed reorder publishes one coherent edit; unfinished dragging does not publish partial state. Effective plans stay available through save failures. Presentation changes should preserve automation behavior and existing saved data.

Research

The current editor is programmatic WinForms. JoinGameAfk's richer champion-priority screen uses WPF with drag/drop and card templates. Visual Studio's designer is not required for either native approach. An embedded React UI could retain the .NET core and enable frontend previews on Linux, but adds WebView2 integration and a frontend build/bridge. Actual Windows host validation remains necessary for all approaches.

Current core commands replace one list per operation. Cross-list moves would need an explicit atomic operation to avoid transient intermediate plans; complex reference gestures should not be imported implicitly.

Throwaway prototype findings

A separate Avalonia 12.1.5/.NET 10 interaction preview runs on the shared Linux desktop. It shows all five role rows, two ranked lanes per role, and a persistent named catalog. Actual UI checks exercised empty-search browsing, Top filtering, partial Tryndamere search, dragging a catalog item into priority 1, dragging within a plan to reorder, and keyboard reordering. The Release build has zero warnings/errors.

This is a layout proposal, not an approved production design. Source and a portable source archive remain under /workspace/shared/afkter-avalonia-prototype/ and /workspace/shared/Afkter-Avalonia-Preview-Source.zip. Sample plans are in memory only and role tags are illustrative. Cross-list moves, data sourcing, persistence integration and tray-host changes remain undecided. The prototype does not use the player’s plan files or League connection.

Open decisions

  • Champion-role data source for the agreed filter.
  • Click-to-add, removal and cross-list drag semantics.
  • Portrait scope and any asset source.
  • Avalonia is selected after independent research. The player also values exploring this framework; React hosting was considered a good alternative. See the independent framework research. The framework is chosen; the final host migration approach and production implementation are not approved yet.
  • Screen layout and final approved design. Build a small throwaway Avalonia prototype with local sample data to evaluate browsing, filtering, adding and reordering; do not connect it to live automation or existing plan files.
