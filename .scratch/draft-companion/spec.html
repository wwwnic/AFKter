AFKtor: focused draft companion

Design approved for ticket breakdown · November 7, 2026 · Product implementation has not started.

Intent

The player prepares a plan, queues in League, and steps away briefly, for example to use the bathroom. AFKtor accepts the ready check and completes supported draft actions according to that plan. Its promise is best-effort execution of the player's choices, not a guarantee of reaching the match when those choices become unavailable.

Extend the existing AFKtor application with a small, reliable draft workflow. Use JoinGameAfk as a source of behavioral and API knowledge, not as code to port wholesale.

Agreed scope and boundaries

  • Draft pick with role-specific ordered pick and ban lists. League's assigned role chooses the plan.
  • Accept ready checks, hover a planned pick, and complete eligible picks and bans.
  • Automation remains enabled across subsequent matches until the player turns it off.
  • A manual ban selection ends ban automation for that draft, with no ban watchdog.
  • When enabling or reconnecting during an ongoing draft, observe only and wait until the next draft to automate. Do not overwrite choices made while AFKtor was not observing.
  • Protect champions teammates are hovering with intent to play. Skip those ban candidates. Another teammate selecting the same champion to ban does not itself protect it; an already banned champion is unavailable.
  • When no configured option is eligible, log why and take no action for that operation. Never choose an unconfigured fallback. Later live edits or changed eligibility may make a planned option available again.
  • Use deliberate hover/lock pacing under normal conditions. When little time remains, skip avoidable waits and prioritize a valid planned action.
  • Default timing works without customization. Advanced settings expose timing controls with reset-to-default support.
  • Plans and settings apply live and autosave, with no Apply button.
  • Include basic status and diagnostic evidence. Custom artwork, themes, elaborate overlays, gameplay automation after draft, queue initiation, and support for additional queue types are outside this release.

The player selected the first approach and the focused release scope.

Player workflow

  1. Configure ordered pick and ban lists for each supported role. Empty lists are permitted and mean no planned action.
  2. Enable automation and queue using League. Existing ready-check acceptance leads into draft monitoring.
  3. Read the assigned role and current draft state. Execute the corresponding plan only during the local player's eligible action window.
  4. Choose the first eligible ban, respecting teammate pick intent. Choose the first eligible pick, hover, then lock according to the normal timing rule.
  5. Observe League to confirm resulting action state; request completion alone is not proof of an applied action.
  6. At draft completion, discard session work and remain enabled for the next match.

Manual pick changes and deadline watchdog

A player manually changing their hovered champion pauses normal automatic pick selection for the rest of that draft. Changing the plan editor is distinct from changing the hover in League.

Setting: after a manual pick changeDeadline behavior
Lock current hover — defaultAttempt to lock the player's current valid hover, including a champion outside the role plan. Do not substitute a planned champion when the hover is invalid.
Use my role planSelect and lock the first currently eligible champion in the latest role plan, even if this replaces the player's manual hover.
Do nothingNo further automated pick selection or locking in this draft.

The watchdog acts shortly before expiry with a practical request margin, rather than relying on a request at zero. If its selected policy has no valid option, log and do nothing. A completed pick is never changed. Disabling automation cancels the watchdog as well as normal pending work.

Live editing and persistence

Every complete editor operation publishes an immutable plan/settings revision: adding or removing a champion, completing a reorder, choosing a policy, or entering a valid timing value. An unfinished drag or invalid numeric input does not publish a partial plan. There is no Apply button.

  • Automation receives a committed in-memory revision immediately. Debounced persistence may follow; disk latency must not block draft decisions.
  • Re-evaluate scheduled work on changes. A changed plan may replace an automatically selected hover; manual-control mode remains in effect until that draft ends.
  • Immediately before dispatch, verify current session, action identity, enabled state, active revision, availability, teammate intent for bans, and deadline. Superseded queued decisions must not dispatch.
  • Changes published after dispatch affect only subsequent work; a sent request cannot be recalled. Reconcile its observed outcome before another action.
  • Serialize actions per local action window. Repeated events and rapid edits must not create parallel requests or restart timing indefinitely.
  • Show unsaved/error status if persistence fails. Preserve the latest effective in-memory plan and retry saving without silently reverting it.

This release extends the original ready-check settings contract: valid live delay edits also re-evaluate an undispatched current countdown from its original detection time. A shorter already-elapsed delay triggers verification; a longer delay moves the deadline without restarting the check. Already skipped checks are not revived. Update the existing documentation and tests that currently capture the delay at detection. This is a proposed consistency decision, not a separately confirmed user choice.

Architecture and quality requirements

  • Retain C#/.NET 10 and the existing tray host. Keep League discovery/transport, draft decisions, editor state, persistence, and diagnostics separate.
  • Represent draft state, local actions, role plans, revisions, and manual-control mode explicitly. Use immutable inputs to a UI-independent decision component and a single serialized execution owner.
  • Inject a controllable clock and simulated client state so timing, cancellation, and interleavings are reproducible without League.
  • Distinguish AFKtor's hover acknowledgments from external player changes using dispatched action evidence and state reconciliation. Ambiguous attribution should yield to manual-control behavior rather than repeatedly overwrite the player.
  • Disconnect, session replacement, disarming, and shutdown invalidate outstanding draft work. Reconnect only after fresh authoritative state; do not replay an old scheduled action.
  • Distinguish a confirmed rejection from an ambiguous request outcome. Reconcile with League before any retry; do not blindly repeat a possibly completed action.
  • Use structured diagnostics for choices, skipped candidates, exhausted lists, revisions, takeover, cancellations, dispatches, and observed outcomes. Extend the existing read-only diagnostics model without making logging a prerequisite for automation.
  • Credentials remain local and excluded from diagnostics. Preserve the existing loopback-only transport boundaries.

Proposed defaults and choices left to implementation

These are author proposals, not additional player-confirmed requirements:

  • Initially support normal Summoner's Rift draft pick with assigned roles. Verify exact supported queue IDs and installed-client action semantics before enabling writes. Ranked, quickplay, and other queues are deferred unless explicitly added.
  • Keep AFKtor disarmed at application startup; enabled state lasts across matches and League restarts within the running AFKtor session, matching existing acceptance behavior.
  • Unknown role, unsupported draft, or insufficient authoritative state means no draft write and a clear status. Do not guess a role.
  • Use normal hover/lock timing and an urgent deadline margin selected from client evidence. The implementation plan must specify initial numeric defaults, supported ranges, and behavior when a draft is first observed near expiry.
  • Use the existing native UI technology for a modest role-plan editor and basic/advanced settings. Exact layout, champion catalog source, and caching approach remain implementation choices; prefer existing local LCU capabilities before adding dependencies.

Verification and delivery

See the proposed ticket breakdown for review. Individual implementation tickets will be published after the breakdown is approved.

Deliver in increments: read-only draft observation and replay fixtures; role plans and live autosave; ban execution; pick/lock/watchdog execution; integrated Windows acceptance. Each increment must preserve ready-check behavior except for the explicitly reviewed live-settings extension.

  • Deterministic tests: all roles; ordered fallback; exhausted plans; teammate pick intent changing before ban dispatch; competing bans; duplicate and out-of-order events; session replacement.
  • Timing tests: normal hover then lock; late entry; expired action; edits during countdown and final verification; no deadline extension from repeated events.
  • Manual-control tests: own acknowledgments do not trigger takeover; manual changes do; all three watchdog policies; policy edited live; invalid hover; exhausted plan.
  • Concurrency tests: old revisions cannot dispatch after newer edits; edits during in-flight requests reconcile safely; disconnect/disarm cancels queued work; ambiguous outcomes do not cause blind duplicate requests.
  • Persistence tests: coherent revisions, rapid edits, save failure, restart recovery, and invalid input. Confirm existing acceptance and diagnostics contracts remain covered.
  • Run the existing build/test workflow, then native Windows UI and installed-League checks. Record client version, queue type, timing evidence, and observed actions. Cross-compilation and simulations alone do not establish live draft readiness.

Success means the supported draft completes unattended when the player's plan remains executable, and every skipped or failed action can be explained. A draft timing out because the configured plan is exhausted is an accepted outcome.
