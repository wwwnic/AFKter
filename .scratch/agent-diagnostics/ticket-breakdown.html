01 — Query live app and connection diagnostics

Blocked by: None.

Delivers: An agent can discover the running app's authenticated localhost API, read a versioned snapshot, and page through correlated startup and connection-change events. The Windows app starts/stops the service automatically; the same real host can be exercised on Linux without WinForms or League.

  • Run identity, ordered event sequences, observation times, and a coherent connection snapshot can be queried. The initial scope is live/current-run evidence; uninstrumented fields are explicitly unavailable.
  • Local discovery publishes the actual endpoint and per-run token with current-user access. Missing/bad credentials and unsupported methods are rejected; no remote listener or action endpoints are introduced.
  • Current-run history, producer work, API pagination, response size, concurrency, and shutdown are bounded. Queue loss/eviction and API startup failures have explicit diagnostic health outcomes.
  • API or collector failure never blocks core operation. A hung sink cannot extend diagnostic shutdown beyond the two-second budget. Test these boundaries from the first slice.
  • Linux integration tests exercise the real listener, discovery, auth, pagination, lifecycle, failure isolation, and secret exclusion. Document an agent's query workflow and new runtime/deployment requirements.

02 — Query retained history across restarts and failures

Blocked by: 01 — Query live app and connection diagnostics.

Delivers: An agent can inspect persisted events after app restart, discover retained runs, and query a single ordered history combining current memory and disk evidence without duplicates.

  • Persist structured JSON Lines records off the application path. Both seven-day retention and a 20,000,000-byte total history limit apply across all retained runs, including the active segment and damaged leftovers.
  • Enforce byte limits before writes; expire records on query and clean up at startup, before writes/queries, and periodically. Storage that cannot maintain the limit becomes degraded rather than continuing to grow.
  • Queries distinguish an empty tail from retained-history eviction, dropped events, corruption, and unavailable persistence. Report only completeness that can be established; abrupt exit may lose the unflushed tail.
  • Recover complete records after restart and tolerate damaged/incomplete tails without crashing the app. Coordinate storage ownership so concurrent instances cannot corrupt history or race the shared byte limit.
  • Bound retries, buffers, record detail, and failure metadata. Throwing, full, slow, unwritable, or locked storage does not change acceptance/cancellation or prevent shutdown.
  • Linux tests with temporary directories and controllable time verify both limits, encoded-byte accounting, restart/prior-run queries, memory/disk merging, corruption, failed cleanup, storage ownership, gaps, and recovery. Document offline access to retained files.

03 — Explain every ready-check decision and accept attempt

Blocked by: 01 — Query live app and connection diagnostics.

Delivers: An agent can reconstruct an observed ready check from detection through scheduling, verification, cancellation, or accept-request outcome using the API, with explicit reasons and timing inputs.

  • Correlate observations, the current connection generation, locally assigned check identity, and accept attempts. Do not invent a server-provided ready-check ID.
  • Record initial/disarmed skips, duplicates/stale updates, arming/delay changes, captured deadlines, cancellations, and failed eligibility conditions at their actual source rather than by polling UI status strings.
  • Expose coherent ready-check state and operation stage in the snapshot, including current/captured delay, observation freshness, and the timing evidence used during final verification.
  • Separate request dispatch, HTTP success/failure, and an unknown post-timeout outcome. Request completion alone must not be presented as League confirming acceptance.
  • Keep detailed useful evidence, with bounded/coalesced repetitions, explicit truncation, and no credentials, raw bodies, or unchecked exception text.
  • Linux tests exercise the real controller plus query API using simulated League and a controllable clock. Cover cancellation, reconnect, duplicate events, stale final reads, timer rejection, delayed verification, once-only dispatch, and diagnostics backpressure/failures without changing existing behavior.

04 — Explain startup, settings, and LCU connection failures

Blocked by: 01 — Query live app and connection diagnostics.

Delivers: An agent can distinguish a missing League Client, inaccessible or invalid discovery data, settings fallback/save errors, and HTTP/WebSocket/session failures, then follow recovery through the same snapshot/event API.

  • Publish safe discovery outcomes, effective setting changes and their reasons, transport/session stages, subscription/seed ordering, and reconnect/loss/recovery events.
  • Include method/fixed route, status, latency, operation stage, typed failure category, and safe stack frames when available. Missing symbols and unknown causes remain explicitly unknown.
  • Keep sensitive lockfile data, authorization values, raw authenticated bodies, diagnostic tokens, unchecked exception messages, and machine-specific absolute paths out of evidence. The API token remains only in its restricted descriptor/authentication handling.
  • Do not change discovery retry timing, LCU destinations, connection identity checks, settings save-before-apply ordering, or existing acceptance/cancellation policy.
  • Linux tests query evidence from real instrumentation using controlled discovery/settings failures and loopback/simulated transport. Verify failure classification, event ordering/correlation, recovery, coalescing, secret exclusion, and continued app operation when diagnostics fail.
  • Update the agent troubleshooting workflow and Windows manual checklist. Explicitly retain the native/live validation limits of Linux tests.
