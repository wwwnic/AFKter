Summary

An agent can reconstruct an observed ready check from detection through scheduling, verification, cancellation, or accept-request outcome. The API exposes explicit decision reasons, correlated identities, coherent state, and the timing inputs that explain why AFKtor acted or skipped work.

Agent diagnostics design · Ticket index and review workflow

Acceptance criteria

  • Query a coherent current ready-check snapshot and a correlated event timeline from the real controller. Include run, connection generation, locally assigned observed-check identity, and accept-attempt identity. Do not invent a server-provided ready-check ID; distinguish current, stale, and unknown observations.
  • Expose arming and configured-delay changes, baseline establishment, detected checks, initial/disarmed skips, duplicate or stale updates, scheduling, and every cancellation cause at the actual decision source. Include old/new effective values, captured delay, deadline, operation stage, observation times, and the relevant connection/check identity.
  • For final verification, record initial/last/returned server timers, actual local elapsed time, the required threshold, and each failed eligibility condition. Preserve conservative initial-pending, backwards-timer, and insufficient-timer skips, including zero configured delay.
  • Distinguish cancellation before request dispatch from cancellation after dispatch. Record dispatch, HTTP completion/failure/status, latency, and uncertainty. A completed HTTP request does not establish that League accepted the match; timeout after dispatch has an unknown outcome and must not cause an automatic retry.
  • Provide detailed safe decision evidence while coalescing repeated identical updates with counts and first/last times. Keep bounded fields and explicit truncation/gap metadata. Credentials, raw authenticated bodies, diagnostic tokens, and unchecked exception messages never enter event/state/query output.
  • Linux tests compose the actual controller, collector and query API with simulated League and a controllable clock. Verify reconstructed evidence for arming/delay edits, duplicate events, initial/disarmed skips, cancellation, reconnect, stale final reads, timer mismatch, delayed verification, and once-only dispatch. Throwing/slow/saturated diagnostics cannot alter deadlines, eligibility, cancellation, session ownership, or shutdown.
  • This ticket depends only on the live query slice: verify its evidence in current-run memory/API without requiring persistence. When the persistence ticket is also present, its generic store must retain/query these versioned records without special-case interpretation.
  • Document how an agent explains an accept, skip, cancellation, or unknown request outcome from the returned evidence. Keep existing tests green, complete a separate subagent code review, and distinguish simulated/loopback coverage from live Windows/League verification.
